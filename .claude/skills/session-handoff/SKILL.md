# Session Handoff

## ทำไมต้องมี skill นี้

บทสนทนาของ Claude Code เก็บอยู่ใน**เครื่องใครเครื่องมัน** — `claude -c` / `claude -r` เรียกคืนได้เฉพาะเครื่องเดิม คนเดิม ทีมนี้มี 2 คน 2 โน้ตบุ๊ก ดังนั้นถ้า context อยู่แค่ใน session ประวัติการคุยจะไม่มีทางข้ามไปหาอีกคนได้เลย

**git repo คือสมองกลางของทีม** ไฟล์ที่ commit แล้ว push ขึ้นไปเท่านั้นที่อีกเครื่องจะเห็น skill นี้ทำหน้าที่ย้าย context จาก "หัวของ session" ลงไปอยู่ใน "ไฟล์ใน repo" ตอนจบงาน และดึงกลับขึ้นมาตอนเริ่มงาน

ที่ต้องระวังคือ ถ้าลืมทำตอนจบงาน อีกคนจะเปิดมาเจอ repo ที่ไม่มีร่องรอยว่าเกิดอะไรขึ้น แล้วต้องเสียเวลาไล่อ่าน diff เอง หรือแย่กว่านั้นคือทำงานซ้ำซ้อนกัน

## สองโหมด

อ่านจากบริบทว่าผู้ใช้กำลังจะ**เริ่ม**หรือ**จบ** ถ้าไม่ชัดให้ถามสั้นๆ ก่อน

---

## โหมด START — เริ่ม session

เป้าหมาย: ตอบให้ได้ว่า "ตอนนี้โปรเจกต์อยู่ตรงไหน และควรทำอะไรต่อ" โดยที่ผู้ใช้ไม่ต้องไปไล่อ่านเอง

1. **ดึงของใหม่ก่อนเสมอ**

   ```bash
   git pull
   git log --oneline -10
   ```

   ถ้า `git pull` ติด conflict หรือมีงานค้างใน working tree ให้หยุดแล้วบอกผู้ใช้ก่อน อย่าพยายาม resolve เองโดยไม่ถาม — งานที่ยังไม่ commit ของอีกคนอาจหายได้

2. **อ่านสถานะจากไฟล์ในลำดับนี้**
   - `docs/HANDOFF.md` — สถานะล่าสุด + blocker (แหล่งข้อมูลหลัก)
   - ไฟล์แผนใน `docs/superpowers/plans/` ที่ยังมี `- [ ]` ค้าง — บอกว่าทำถึง step ไหน
   - `git log` ตั้งแต่วันที่ใน HANDOFF.md — จับว่ามีงานที่ทำไปแล้วแต่ยังไม่ได้เขียนลง handoff ไหม

3. **รายงานผู้ใช้เป็นภาษาไทย สั้น กระชับ** ครอบคลุม 3 อย่าง:
   - มีอะไรเปลี่ยนตั้งแต่ครั้งที่แล้ว (อีกคนทำอะไรไป)
   - ตอนนี้ค้างอยู่ที่ไหน / blocker คืออะไร
   - ทำอะไรต่อได้เลย (เสนอ 1-2 ทางเลือกที่ชัดเจน ไม่ต้องแจกแจงทุกความเป็นไปได้)

   ถ้าเจอว่า HANDOFF.md ไม่ตรงกับ git log (เช่น มี commit ใหม่ที่ handoff ไม่ได้พูดถึง) ให้บอกตรงๆ ว่าไม่ตรง แล้วเชื่อ git log เป็นหลัก เพราะ commit คือสิ่งที่เกิดขึ้นจริง ส่วน handoff คือสิ่งที่มีคนอุตส่าห์เขียน — อาจลืมอัปเดตได้

## โหมด END — จบ session

เป้าหมาย: อีกคนเปิดพรุ่งนี้แล้วทำงานต่อได้ทันทีโดยไม่ต้องถามใคร

1. **ทบทวนว่า session นี้เกิดอะไรขึ้นบ้าง** — ไล่จาก `git diff`, `git status` และบทสนทนาที่ผ่านมา

2. **ติ๊ก checkbox ในไฟล์แผน** ถ้ามี step ไหนทำเสร็จจริงในรอบนี้ (`- [ ]` → `- [x]`) นี่เป็นสัญญาณที่อีกคนอ่านง่ายที่สุดว่างานเดินไปถึงไหน

3. **อัปเดต `docs/HANDOFF.md`** — เขียนทับส่วนที่ล้าสมัย ไม่ใช่ต่อท้ายไปเรื่อยๆ (handoff ที่ยาวขึ้นทุกวันจะไม่มีใครอ่าน) ใช้โครงนี้:

   ```markdown
   # Handoff — <ชื่องาน>

   > อัปเดตล่าสุด: <YYYY-MM-DD> โดย <ชื่อคน>

   ## ทำอะไรไปในรอบนี้
   - <สิ่งที่ทำเสร็จ พร้อม commit hash ถ้ามี>

   ## ค้างอยู่ตรงไหน
   - <งานที่เริ่มแล้วยังไม่จบ + อยู่ในไฟล์ไหน>

   ## Blocker (รออะไรอยู่)
   - [ ] <สิ่งที่รอคนอื่น/รอข้อมูลจากภายนอก>

   ## ทำอะไรต่อ
   1. <step ถัดไปที่ชัดเจนพอจะลงมือได้เลย>
   ```

   สิ่งที่ทำให้ handoff มีประโยชน์จริงคือ **ความจำเพาะ** — "แก้ bug sync" ไม่ช่วยอะไร แต่ "`sheet-push` ยิงสำเร็จแล้วแต่แท็บ ตี๋น้อย ยัง 403 เพราะยังไม่ได้เชิญ service account เป็น Editor" ทำให้อีกคนลงมือต่อได้ทันที

   เขียนเป็นภาษาไทย เพราะทีมนี้สื่อสารกันเป็นไทย

4. **เช็ค build ถ้าแตะ frontend**

   `push` เข้า `main` ทำให้ Vercel deploy เว็บขึ้น production ทันที ไม่มีขั้นตอนกดยืนยันที่ Vercel ดังนั้นถ้ารอบนี้มีการแก้ไฟล์ใน `frontend/` ให้รัน `cd frontend && npm run build` ก่อน ถ้าไม่ผ่านให้หยุดแก้ก่อน อย่าไปต่อ

5. **ตรวจก่อน แล้วขออนุมัติ — อย่า commit + push เอง**

   ขั้นนี้สำคัญเพราะ push เข้า `main` = ขึ้น production ทันที และ commit ที่พลาดจะกลายเป็นสิ่งที่อีกคนต้อง pull ไปเจอ ให้ทำตามลำดับ:

   ```bash
   git status
   git diff --stat
   ```

   - ดูว่ามีไฟล์ที่ไม่ควรขึ้น repo ปนมาไหม — โปรเจกต์นี้มี service account key และ secret หลายตัว ถ้าเห็นไฟล์ `.json` ที่หน้าตาเหมือน credential, ไฟล์ `.env`, หรืออะไรที่มีคำว่า key/secret/token ให้หยุดถามก่อน
   - **แสดงให้ผู้ใช้ดูว่าจะ commit ไฟล์อะไรบ้าง และร่างข้อความ commit ให้ดูก่อน**
   - **รอให้ผู้ใช้ยืนยัน** แล้วค่อย `git add` → `git commit` → `git push`

   ถ้าผู้ใช้อยากแก้ข้อความ commit หรือเอาบางไฟล์ออก ให้แก้ตามแล้วยืนยันอีกรอบ

6. **สรุปให้ผู้ใช้ 2-3 บรรทัด** ว่า push อะไรขึ้นไป และอีกคนจะเห็นอะไรตอนเปิดมา ถ้ารอบนี้แตะ `frontend/` ให้บอกด้วยว่าเว็บจริงจะอัปเดตตามภายในไม่กี่นาที

## เรื่องแบ่งงานกันไม่ให้ชน

ทีมนี้มี 2 คน งานส่วนใหญ่ไม่ควรชนกันอยู่แล้ว แต่ถ้าจะแก้ไฟล์เดียวกันในเวลาไล่เลี่ยกัน ให้แยก branch:

```bash
git checkout -b <ชื่อคน>/<งานที่ทำ>
```

แล้วเปิด PR ด้วย `gh pr create` ก่อน merge เข้า main — วิธีนี้ทำให้เห็นชัดว่าใครแก้อะไร และ merge conflict จะโผล่ตอน PR ไม่ใช่ตอนอีกคนกำลังทำงานอยู่

ถ้าทำงานคนละส่วนกันชัดเจน (เช่น คนหนึ่งทำ backend อีกคนทำ frontend) push เข้า main ตรงๆ ก็พอ ไม่ต้องเพิ่มพิธีกรรมโดยไม่จำเป็น
