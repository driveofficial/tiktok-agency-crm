## สิ่งที่ทำ (รายละเอียด)

### #6 — เริ่มใช้ git (version control)

**อธิบาย**
- *ก่อนแก้:* แก้แอปแล้วถ้าพัง ไม่มีทางย้อนกลับไปตอนที่ยังใช้ได้ ต้องมานั่งไล่แก้กลับเองทีละจุด
- *หลังแก้:* ทุกครั้งที่แก้ ระบบจดจำสถานะไว้ให้ ถ้าพังก็สั่งย้อนกลับไปจุดที่ยังดีได้ทันที

**ทำอะไร**
- `git init` ในโฟลเดอร์โปรเจกต์
- สร้าง `.gitignore` (กัน `node_modules/`, `dev/preview.html`, log)
- commit แรก = snapshot โค้ดเดิมทั้งหมดก่อนแตะอะไร
- commit สอง = เครื่องมือ dev ทั้งชุด

**ส่งผลยังไง**
- มีประวัติการแก้โค้ด ย้อนกลับได้ถ้าพัง (เดิมไม่มีเลย = เสี่ยงมากกับโค้ด 300KB+)
- เห็นชัดว่าแต่ละครั้งเปลี่ยนอะไรบ้าง
- พร้อมต่อยอด clasp / GitHub ในอนาคต

### #1 — Local preview (แก้แล้วเห็นผลทันที ไม่ต้อง deploy)

**อธิบาย**
- *ก่อนแก้:* อยากดูว่าที่แก้ไปหน้าตาเป็นยังไง ต้องคัดลอกไฟล์เข้า Google กดเผยแพร่ แล้วรอหลายนาที ทำวันละหลายรอบ = เสียเวลามาก
- *หลังแก้:* เปิดแอปเวอร์ชันทดลองในเครื่องได้เลย ใช้ข้อมูลจำลอง (ไม่ยุ่งกับข้อมูลจริงของทีม) แก้เสร็จรีเฟรชก็เห็นผลภายในไม่กี่วินาที

**ทำอะไร**
- `dev/preview.mjs` — รวมไฟล์ HTML ทุกส่วนเป็นไฟล์เดียว `preview.html` เปิดในเบราว์เซอร์ได้เลย
- ใช้ **mock data** (ข้อมูลจำลอง) — อาศัยสาขา mock ที่มีอยู่แล้วใน `utils.html` ตอน `window.isGAS` เป็น false จึงไม่ต้องต่อ Google Sheet
- `dev/serve.mjs` — static server เล็กๆ (เพราะ Chrome บล็อกการเปิด `file://` ตรงๆ)

**ตรวจสอบแล้ว (จริงในเบราว์เซอร์)**
- หน้า list การ์ด render ครบ (ครีเอเตอร์, เช็คลิสต์, สถานะ, quick-filter)
- หน้า Dashboard render ครบ (กราฟ Recharts, สถิติ)
- console **ไม่มี error**

**ส่งผลยังไง**
- loop พัฒนาจาก "แก้ → คัดลอก → deploy → รอ → ดู" (หลายนาที) เหลือ "แก้ → refresh" (ไม่กี่วินาที)
- นี่คือตัวปลดล็อกที่สำคัญสุด — งานที่เหลือทุกอย่างเร็วขึ้นตาม

### #3 — Precompile JSX (แอปโหลดเร็วขึ้น โดยเฉพาะมือถือ)

**อธิบาย**
- *ก่อนแก้:* ทุกครั้งที่มีคนเปิดแอป เครื่องต้องประมวลผลโค้ดสดๆ ก่อนถึงจะแสดงหน้าจอได้ ทำให้เปิดช้าและกินแรงเครื่อง มือถือรุ่นกลางๆ จะรู้สึกอืด
- *หลังแก้:* ย้ายงานประมวลผลนั้นมาทำไว้ล่วงหน้าตั้งแต่ตอนเตรียมไฟล์ พอมีคนเปิดแอปก็แสดงผลได้เลย เปิดไวขึ้นและลื่นขึ้นบนมือถือ

**ปัญหาเดิม (เชิงเทคนิค)**
- แอปคอมไพล์ JSX ในเบราว์เซอร์ทุกครั้งที่โหลด ด้วย Babel standalone (~3MB) = ช้า กิน CPU มือถือ (ทั้งที่ผู้ใช้หลักคือทีมงานภาคสนามบนมือถือ)

**ทำอะไร**
- `dev/build.mjs` — คอมไพล์ JSX เป็น `React.createElement` ล่วงหน้าด้วย esbuild แล้วเขียนไป `dist/`
- transform แบบ in-place (จงใจไม่ใส่ `format`) = ผลลัพธ์คือไฟล์ต้นฉบับ "ลบ JSX" เท่านั้น scope และ `window.*` เดิมคงอยู่ครบ ไม่เปลี่ยน architecture
- ตัด Babel CDN ออกจาก `index.html`

**ส่งผลยังไง**
- หน้าเว็บโหลดเร็วขึ้น ไม่ต้องดาวน์โหลด/รัน Babel 3MB ทุกครั้ง
- ลดภาระ CPU มือถือ = ลื่นขึ้นบนเครื่องกลางๆ
- **โครงสร้างไฟล์/ชื่อไฟล์/จำนวนเหมือนเดิมทุกอย่าง** ทีมยังคัดลอกเข้า Apps Script แบบเดิม — แค่คัดจาก `dist/` แทน root

### #5 — Tests (กันโค้ดพังเงียบ)

**อธิบาย**
- *ก่อนแก้:* จุดที่พังง่ายและมองไม่เห็นคือการอ่านข้อมูล เช่น การแปลงปี พ.ศ. เป็น ค.ศ. หรือการเดาว่าหัวคอลัมน์ในชีตหมายถึงอะไร ถ้าเพี้ยนขึ้นมา สถิติจะผิดโดยไม่มีใครสังเกตจนกว่าจะสายเกินไป
- *หลังแก้:* มีชุดตรวจสอบอัตโนมัติคอยเช็กจุดเสี่ยงเหล่านี้ให้ครบด้วยคำสั่งเดียว ถ้าแก้แล้วเผลอทำพัง จะรู้ทันทีก่อนเอาขึ้นใช้จริง

**ทำอะไร**
- `dev/tests/` — โหลด **โค้ดจริง** จาก `code.gs` + `utils.html` ผ่าน `node:vm` (ไม่ก๊อปโลจิกมาเขียนซ้ำ = ไม่มี drift ระหว่างเทสต์กับของจริง)
- ครอบคลุมฟังก์ชัน pure ที่เสี่ยงพังเงียบสุด:
  - **วันที่ พ.ศ./ค.ศ.** — `parseDate`, `normYear`, `formatDateISO`, `getStartOfWeek` (2569 → 2026, รูปแบบ DD/MM/YYYY, ค่าว่าง)
  - **fuzzy match หัวคอลัมน์ไทย** — `getColumnConfig` (หัวเปลี่ยนแล้วยัง match ถูก)
  - **ชื่อที่แสดง / pipeline stage** — `extractTiktokUsername`, `getDisplayName`, `getPipelineStage`

**ผล:** 15/15 ผ่าน

**ส่งผลยังไง**
- โลจิกที่แตกง่ายเงียบๆ (แปลงปีไทย, จับหัวคอลัมน์) มีตาข่ายกันไว้แล้ว
- แก้โค้ดครั้งหน้าแล้วเผลอทำพัง จะรู้ทันทีจาก `npm test` แทนที่จะไปเจอบนแอปจริง
